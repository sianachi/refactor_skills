# SQL and Postgres

Read this when the scope touches SQL, whether written by hand or generated by an ORM. It adds to SKILL.md.

## Generating test data

Load data at realistic scale in seconds with `generate_series`. Seed the randomness so runs are repeatable:

```sql
SELECT setseed(0.42);
INSERT INTO orders (customer_id, status, total_cents, created_at)
SELECT 1 + (random() * 9999)::int,
       (ARRAY['open','paid','shipped','returned'])[1 + (random() * 3)::int],
       (random() * 100000)::int,
       now() - (random() * interval '730 days')
FROM generate_series(1, 500000);
ANALYZE orders;
```

Skew the distributions the way production would be skewed: a few large customers, a rare status. Uniform data hides the plans that real data triggers. Always `ANALYZE` after a bulk load, or the planner works from stale statistics.

## Measuring

- **Query plan**: `EXPLAIN (ANALYZE, BUFFERS) <query>`. Look for `Seq Scan` on large tables, high `Rows Removed by Filter`, `Sort` nodes spilling to disk, and nested loops with large outer sides.
- **Queries per request**: snapshot `SELECT xact_commit FROM pg_stat_database WHERE datname = current_database()` before and after one request. Each autocommit statement counts once, which is close enough to spot N+1. Use `pg_stat_statements` if the extension is enabled.
- **Rows read**: deltas of `seq_tup_read` and `idx_tup_fetch` in `pg_stat_user_tables` show whether a request scanned the table.
- On a small table Postgres seq-scans no matter what indexes exist, so judge plans on the generated data only.

## Pagination

Keyset pagination with row-value comparison, and an index whose column order and directions match the `ORDER BY`:

```sql
-- first page
SELECT id, title, created_at FROM notes ORDER BY created_at DESC, id DESC LIMIT 51;
-- next page
SELECT id, title, created_at FROM notes
WHERE (created_at, id) < ($1, $2)
ORDER BY created_at DESC, id DESC LIMIT 51;

CREATE INDEX CONCURRENTLY notes_created_id_idx ON notes (created_at DESC, id DESC);
```

- Fetch `limit + 1` rows: the extra row tells you there's a next page, without a `COUNT`.
- Row comparison `(a, b) < (x, y)` only works when every column sorts in the same direction. With mixed directions, write it out: `a < x OR (a = x AND b > y)`.
- Nullable sort columns break keyset pagination: sort with `NULLS LAST` and handle the null cursor explicitly, or sort by a non-null column.
- With filters, put the equality columns first in the index, then the sort columns: `(status, created_at DESC, id DESC)`.
- `COUNT(*)` for a total reads every matching row. Don't add exact totals to paginated responses on large tables unless the UI shows them. Return `hasMore` or `nextCursor` instead, or an estimate from `pg_class.reltuples` if a rough number is enough.
- `OFFSET n` reads and throws away n rows, so deep offsets get slower linearly. Cap the depth when the UI needs page numbers.

## Moving filters into SQL with the same semantics

| Client code | Same thing in Postgres |
|---|---|
| `s.toLowerCase().includes(q.toLowerCase())` | `strpos(lower(s), lower($1)) > 0`, which needs no escaping, or `s ILIKE '%' \|\| $1 \|\| '%'` with `\`, `%` and `_` escaped in `$1` (backslash is the default `LIKE` escape) |
| `s.startsWith(q)` | `s LIKE $1 \|\| '%'`, escaped. Add an index with `text_pattern_ops` when the database collation isn't `C` |
| `a === b` on strings | `a = b` (case-sensitive, like JS) |
| `array.sort((x, y) => x.name.localeCompare(y.name))` | `ORDER BY name COLLATE "<locale>"`. JS `localeCompare` follows ICU locale rules |
| default `array.sort()` or `<` on strings | `ORDER BY name COLLATE "C"` (code-point order; JS compares UTF-16 code units, which differs only for characters outside the BMP) |
| `items.length` after a filter | `COUNT(*)` with the same `WHERE` |
| sum or average in JS | `SUM`/`AVG`. Watch the types: `SUM(int)` returns `bigint`, `SUM`/`AVG` of `numeric` return `numeric`, and some drivers return these as strings |

- `lower()` follows the database's collation and Unicode rules, which can differ from JavaScript and .NET for characters like `İ`, `ß` and `ς`. Test accented and non-Latin inputs in the harness.
- A `NULL` column never matches `LIKE` or `strpos`. If the old client code treated a missing value as `""`, use `coalesce(col, '')`.
- The database's default collation decides `ORDER BY` for text (`en_US.UTF-8` sorts case-insensitively and ignores punctuation at first pass; `C` doesn't). Check `SELECT datcollate FROM pg_database WHERE datname = current_database()` (`SHOW lc_collate` is gone in Postgres 16+) and reproduce the old client order exactly.

## Indexes

- **Check filter combinations one by one.** For every query with optional filters, list each combination the API allows (none, A, B, A and B), run `EXPLAIN (ANALYZE, BUFFERS)` for each on skewed data, and compare the buffers read with the rows returned. Reading thousands of buffers to return a few dozen rows means an index is missing for that combination. The usual case: a big customer plus a rare status, where a single-column index on `customer_id` still reads every one of that customer's rows. Add the composite index `(customer_id, status)` with the equality columns first.
- **B-tree** for equality, ranges and `ORDER BY`. In a composite index, equality columns go first, then range or sort columns.
- **Partial index** when queries always filter on one value: `CREATE INDEX ... ON orders (created_at) WHERE status = 'open'`.
- **Expression index** for a function in the `WHERE`: `CREATE INDEX ... ON users (lower(email))`.
- **Substring search** (`ILIKE '%q%'`, `strpos`): B-trees can't help. A trigram GIN index can (`CREATE EXTENSION IF NOT EXISTS pg_trgm; CREATE INDEX ... USING gin (title gin_trgm_ops)`), but the extension needs privileges that some managed hosts don't grant. If you can't add it, keep the query correct, paginate it, and report the remaining scan.
- **Foreign keys** aren't indexed automatically in Postgres: index the referencing column when you join or filter on it.
- **`CREATE INDEX CONCURRENTLY`** can't run inside a transaction block, and a failed build leaves an `INVALID` index that must be dropped before retrying. Use one statement per migration step. Make it rerunnable with `IF NOT EXISTS`.
- Every index slows writes and takes space. Add only the ones your changed queries use, and prove each with `EXPLAIN`.

## Avoiding N+1 and over-fetching

- Replace a query per item with a join, or with one query using `WHERE id = ANY($1)` and an array parameter, then assemble the results in code.
- Nested results in one round trip: `json_agg` or `array_agg` with a `GROUP BY`.
- Select only the columns the caller uses. Large `text`, `jsonb` and `bytea` values are stored out of line (TOAST) and only read when selected, so leaving them out of list queries saves real I/O.

## Exports

- `COPY (SELECT ...) TO STDOUT WITH (FORMAT csv, HEADER)` streams CSV straight from the server and is the fastest export. Its quoting, null and number formatting differ from most CSV libraries, so use it only when the output is byte-identical to the old export, or when the export format isn't a contract.
- Otherwise stream rows through a server-side cursor or the driver's row iterator. For very long exports, run keyset batches (`LIMIT 5000` per batch) so no single query holds a snapshot open for minutes.
